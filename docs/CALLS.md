# Voice and video calls

## Product decision

The app will keep iOS 16 as its minimum and avoid the AGPL-licensed Element Call packages. The custom native call host will use the Apache-2.0 LiveKit client SDKs and a self-hosted LiveKit SFU. Android is pinned to `io.livekit:livekit-android:2.29.0`; iOS is pinned to LiveKit Swift `2.17.0`. LiveKit Swift declares iOS 13 as its minimum platform and supports Swift 5 language mode, so the package's stated platform and language settings fit this app's iOS 16 / Swift 5 target. It requires Swift tools 6.1 (Xcode 16.3 or newer) to resolve and build. See the [Swift package manifest](https://github.com/livekit/client-sdk-swift/blob/2.17.0/Package.swift), [Swift license](https://github.com/livekit/client-sdk-swift/blob/2.17.0/LICENSE), and [Android SDK license and release](https://github.com/livekit/client-sdk-android/tree/v2.29.0).

## Architecture

- Matrix remains the identity, encrypted conversation, and call-control transport.
- The namespaced `m.room.message` envelope is reserved for nonsecret call-control metadata and cannot carry a media key. A verified 1:1 peer does not prove that all of that user's devices are verified, so retained room events are not an approved transport for call keys. Android now sends its fresh media key only in an Olm-encrypted custom to-device invitation addressed to explicitly cross-signing-verified device IDs.
- Each call creates a fresh 256-bit media key on a client and passes it to LiveKit's native E2EE key provider before connecting. The LiveKit token service issues short-lived, least-privilege join tokens after validating the caller's Matrix access token and current room membership; it must never receive a media key.
- A random per-call LiveKit room name and random participant identity avoid reusing a stable Matrix identifier at the SFU. Media and LiveKit data channels use the SDK's frame encryption. Signaling metadata and IP/network details remain visible to the SFU and network peers; E2EE does not make a call anonymous.
- LiveKit join tokens set `canPublish: true` because both pinned native SDKs require that flag before attempting a local publish; `canPublishSources` remains the restrictive allowlist containing only `camera` and `microphone`. Screen-share sources are not granted.
- A changed or unverified peer identity must block call setup. The current trust projection only covers one-to-one rooms, so the first implementation is limited to verified one-to-one calls. Group calls stay disabled until the app can prove every recipient device meets the selected trust policy.
- Each call uses a new key and expires independently. Hang-up stops capture, disconnects, and drops the app's room/provider references; the pinned LiveKit SDK exposes no public API to prove or force an immediate wipe of every internal key copy. Invitations must expire quickly; replayed, malformed, or stale invitations are ignored.

LiveKit documents that E2EE keys must be generated and distributed out of band, and that its signaling/control plane remains visible to the LiveKit server even when media frame encryption is enabled. Android's verified-device send path now closes the initial outbound key-routing gap, but call setup is not yet a complete user flow. See [LiveKit encryption](https://docs.livekit.io/transport/encryption/), [Android E2EE setup](https://docs.livekit.io/transport/encryption/start/), and the [self-hosting deployment guide](https://docs.livekit.io/transport/self-hosting/deployment/).

The Rust FFI has encrypted custom to-device send and receive primitives, merged upstream as PRs [#6981](https://github.com/matrix-org/matrix-rust-sdk/pull/6981) and [#6980](https://github.com/matrix-org/matrix-rust-sdk/pull/6980). The app now uses a private Android AAR built from SDK revision `2a3db80e99fe322b9849325a182dc8a634fb20d4` plus the verified-device query patch. The AAR includes all four Android ABIs; the locally stripped AAR SHA-256 is `052D255692E5E6516A46AD62B8331687333F191008609EF32C8404B42ED3628C`. The query refreshes the peer identity, rejects absent, unverified, or violating identities, and returns only cross-signing-verified device IDs. `startSecureCall` rejects unencrypted or non-direct rooms, rooms with more than two members, empty device lists, wildcard IDs, and duplicate IDs; it sends the key only to the explicit recipient map and aborts on any delivery failure. It now requests a server-signed call handle and short-lived LiveKit token from the homeserver's same-origin call-auth endpoint. `authorizeIncomingSecureCall` rechecks encrypted direct-room membership and peer verification before requesting a fresh join token. These paths compile and have focused local tests, but have not been validated against a live deployment. User-level `UserIdentity.isVerified()` alone is not used as a substitute for per-device trust.

Android now has permission-gated voice/video call controls, encrypted accept/decline/hang-up controls, LiveKit session setup, and a remote video renderer with detach/release handling. It disables the outgoing microphone and camera until an encrypted peer acceptance arrives. Remote video and media behavior still need testing against a live LiveKit server and physical devices; background incoming-call wakeup is not implemented. iOS has a new same-origin call-auth HTTP client source, but it is not integrated with the app, has not compiled here, and the currently pinned Swift Matrix wrapper still lacks the cross-signed device query needed to send call keys safely. Cross-platform call interoperability remains unimplemented.

Incoming messages must continue to require Olm decryption, sender/device metadata, strict cross-signing trust, matching encrypted-room membership, and fresh call IDs. The patch and reproducible Android build notes are in [`ops/sdk-build/README.md`](../ops/sdk-build/README.md). iOS pins `26.09.07` (iOS 16, Swift 5), which predates encrypted custom to-device send/receive and lacks the device inventory API. No newer official Swift wrapper exposing these methods was found. A matching internally generated Swift XCFramework/package from the same Rust SDK revision is still required; that needs macOS/Xcode for generation, packaging, build, and validation. Never substitute an unencrypted endpoint or retained timeline event for call-key transport. See the [Matrix Rust SDK FFI changelog](https://github.com/matrix-org/matrix-rust-sdk/blob/main/bindings/matrix-sdk-ffi/CHANGELOG.md), [Kotlin wrapper releases](https://github.com/matrix-org/matrix-rust-components-kotlin/releases), and [Swift wrapper releases](https://github.com/matrix-org/matrix-rust-components-swift/releases).

## Implementation status

Android has a user-facing voice/video start and accept/decline/hang-up flow wired through verified-device Olm key transport, homeserver call authorization, and LiveKit E2EE session setup. Permission prompts bind acceptance to the exact invitation ID and room so a replaced invite cannot be accepted by a stale callback. The same-origin auth client and Android flow compile; focused unit tests cover protocol validation, but live call setup and media remain unverified because the local deployment is unavailable. iOS has a same-origin call-auth HTTP client source and standalone LiveKit media-session component, but they are not integrated with Matrix call key transport or UI; the pinned Swift Matrix wrapper lacks the required verified device query. Cross-platform call interoperability is unimplemented. Do not describe calls as shipped until both platforms, live token/media flow, interoperability, and SFU ciphertext checks pass.

The Windows development host has no Xcode or iPhone. Android builds and emulator validation can continue here. An Xcode archive, CallKit validation, signed iOS build, physical-device testing, and Android-to-iOS call acceptance require access to a Mac/Xcode and iPhone.

## Incoming call behavior

Call invitations must not carry media keys in persistent room events. A future implementation may use encrypted Matrix room events for nonsecret call-control metadata only after deciding the retention and replay policy; the media key must use verified-device Olm-encrypted to-device delivery. Background wake-up requires a separate platform implementation: Android call notifications/foreground service and iOS PushKit plus CallKit. Generic message push is not sufficient. Push payloads must remain generic and contain no call key, media, or message content. APNs/FCM credentials and signed-device acceptance remain external requirements. See [Apple's PushKit response requirements](https://developer.apple.com/documentation/pushkit/responding-to-voip-notifications-from-pushkit).

## Deployment requirements

The private deployment needs a publicly reachable LiveKit service with trusted TLS, an authenticated token endpoint, and firewall access for the configured ICE/TURN transports. TURN/TLS or a tested relay route is required for restrictive networks. The service's API key and secret stay server-side; no shared development token or API secret may be embedded in an app. The homeserver domain, VPS, TLS, firewall, persistent storage, and backups are not yet provisioned. See [LiveKit's port and firewall guide](https://docs.livekit.io/transport/self-hosting/ports-firewall/).

## Acceptance checks

- Verified Android and iOS users can start, answer, decline, and hang up voice and video calls in both platform directions.
- A call is refused if the room is unencrypted, the peer trust is unknown/unverified/changed, token authorization fails, or the media key is missing or invalid.
- The SFU and token service cannot decode media frames or obtain Matrix-encrypted call keys.
- Room membership changes, new/unverified devices, replayed invitations, call expiry, and hang-up/rejoin cause the expected key and authorization behavior.
- Mute, camera toggle/switch, Bluetooth/headsets, audio interruptions, app backgrounding/PiP, network handover, and TURN-only connectivity work on physical devices.
- CallKit, Android incoming-call notifications, push wake-up, and generic push payloads are validated on signed devices; payloads and logs contain no plaintext or keys.
- Deployment restart, resource limits, firewall exposure, and backup/restore behavior are verified.
